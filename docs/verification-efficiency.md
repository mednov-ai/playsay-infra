# Экономная организация проверок

## Вывод из RF dev acceptance

Автоматизация уже есть, но единичные проверки, временные browser scripts и ручной разбор результатов не образуют воспроизводимый набор. Перенос действий в скрипт экономит контекст только тогда, когда скрипт сам проверяет результат и возвращает компактную сводку. Частый опрос скрипта и чтение полных логов сохраняют лишние расходы. Точная экономия токенов пока не измерена.

## Порядок работы

Перед выполнением OpenSpec задач составить короткую матрицу: требование → существующая проверка → условие успеха → что заставляет повторить проверку. Несколько задач могут ссылаться на один результат. Не создавать отдельный одинаковый smoke на каждый checkbox.

| Изменение | Минимальный набор | Когда расширять |
|---|---|---|
| Только документы | Diff и проверка ссылок/согласованности | Изменились команды или acceptance contract |
| GeoIP reader/updater | `scripts/test-honey-school-geoip.py` | Изменились runtime dependencies, база или политика активации |
| nginx GeoIP policy | Контракт и `scripts/test-geoip-nginx-runtime.py` | Изменились navigation/auth исключения: browser journey |
| RF edge / TURN | `scripts/test-rf-edge-dev-contract.py`, затем dev allocation и parity по runbook | Изменились credentials, firewall, NAT, SFU или ICE: media journey |
| Login/return path | Целевые auth tests и browser deep-link journey | Изменились issuer, origins или cookie/session policy |
| Панель диагностики | Целевые UI tests и один browser shortcut scenario | Layout/theme: desktop/mobile; media interpretation: активный урок |

Команды запуска и prerequisites берутся из самих скриптов и runbook. TURN allocation подтверждает только allocation, HTTP — доступность endpoint, synthetic GeoIP — логику политики. Они не заменяют RTP, реальную RF сеть или production canary.

Для изменившегося dev runtime сначала выполнить дешёвые проверки readiness/config/API. После их успеха — только затронутый browser journey. Длительную media проверку запускать после короткой проверки двустороннего RTP и необходимых действий, включая запуск screen share, если он входит в acceptance. Сбор RTT/jitter/loss, ICE и signaling transitions выполняет скрипт; агент не участвует в цикле измерения.

## Повторное использование evidence

Результат привязан к времени, environment, script revision, application image digest, relevant configuration revision, browser version и профилю сети. Для GeoIP дополнительно фиксируется версия базы. Секреты и их хэши не входят в отчёт; ротация обозначается несекретной revision или требует нового прогона.

Повторять затронутый сценарий при изменении его зависимости, drift, новом симптоме или необходимости подтвердить текущее состояние. Не повторять длинный прогон после правки документации. Старый результат не является свидетельством текущей readiness: при выкладке нужна новая короткая проверка состояния.

При ошибке открыть только относящийся к ней фрагмент evidence и запустить минимальное воспроизведение. После исправления повторить упавший сценарий и зависимые проверки. Не перезапускать весь набор ради зелёного результата. Возможный flaky retry явно помечать; первый сбой сохранять, причину расследовать. Нет доказательства — статус UNKNOWN/BLOCKED, не PASS.

## Контракт будущего runner

Единого runner пока нет. Реализовывать его небольшими шагами поверх существующих скриптов, без нового тестового фреймворка:

1. Общий локальный запуск выбранных contract checks с timeout и компактным JSON/text summary; никаких remote действий по умолчанию.
2. Перенести проверенные временные сценарии auth, shortcut и двух участников в `playsay-platform/scripts/smoke`, выделив общие login/cleanup helpers. Учётные данные получать существующим workflow только в память. Fixtures удалять в `finally`; ошибки cleanup отражать в итоговом статусе.
3. Добавить dev runtime/media profiles и подключить их к подходящим CI stages. Production профиль должен быть отдельным, с существующими ограничениями и разрешением на запуск; автоматического fallback с dev на prod нет.

Сводка содержит check ID, PASS/FAIL/SKIP/UNKNOWN, duration, environment, revisions, метрики, безопасную причину и путь к очищенному artifact. Общий ненулевой exit code нужен при обязательной проверке без PASS, включая timeout/cleanup failure. Скрипт выдаёт итог при завершении и ограниченные события смены стадии; не требует частого опроса агентом.

Не сохранять сырые токены, headers, callback URLs, пользовательские данные или network traces с credentials. Скриншоты — для визуального acceptance или ошибки; успешные невизуальные проверки обходятся без них. В чат поступают краткая сводка и ссылки; полные очищенные artifacts читаются только при необходимости.

## Критерий эффективности

На следующих сравнимых изменениях учитывать число запусков и повторов, browser/runtime минуты, количество tool calls и объём выведенных в контекст данных. Процент экономии лимита не обещать без измерения. Успех — тот же набор подтверждённых требований при меньшем числе повторов и меньшем объёме контекста, без скрытых ошибок и пропущенных acceptance gates.
